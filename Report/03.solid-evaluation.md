## 3. 원칙별 상세 평가

### 3.1 S — Single Responsibility (단일 책임)

**질문:** `TVChannelController`가 단일 책임만 갖는가? 채널 관리 / 선호 채널 / 입력 처리가 분리됐는가?

| 점수 | **5 / 10** |
|---|---|

#### 현재 구조

`TVChannelController`는 다음 책임을 **동시에** 보유한다.

| 책임 | 관련 멤버·메서드 |
|---|---|
| 숫자 입력 처리 | `inputBuffer_`, `pressNumber()`, `pressConfirm()`, `pressOther()` |
| 채널 적용·유효성 | `isValidChannel()`, `applyChannel()`, `tuner_.setCH()` (의도) |
| 선호 채널 관리 | `favorites_`, `isFavorite()`, `addFavorite()`, `pressFavorite()`, `pressNextFavorite()` |
| 리모컨 이벤트 조율 | `press*` public API 전체 |

```7:41:include/TVChannelController.h
class TVChannelController {
    ITuner& tuner_;
    int inputBuffer_ = -1;
    std::vector<int> favorites_;

    bool isValidChannel(int ch) const { ... }
    bool isFavorite(int ch) const { ... }
    void applyChannel(int ch);

public:
    void pressNumber(int digit);
    void pressConfirm();
    void pressFavorite();
    void pressNextFavorite();
    void pressOther();
    // ...
};
```

#### 판정

- **분리되지 않음:** 채널 관리(튜너 연동), 선호 채널(목록·정렬·다음 채널), 입력 처리(버퍼·두 자리 완성)가 **별도 클래스 없이** 한 컨트롤러에 모여 있다.
- **현재 규모:** TDD 연습용·기능 수가 적을 때는 “리모컨 컨트롤러” 하나로 묶는 것도 실용적이다.
- **기능 완성 후:** README의 `pressNumber` / `pressFavorite` / `pressNextFavorite` 시나리오가 구현되면 **변경 이유가 서로 다른 3가지 정책**이 한 클래스에 쌓인다.

#### 개선 방향

| 추출 클래스 | 담당 |
|---|---|
| `ChannelInputBuffer` | 숫자 입력, 두 자리 완성, `pressOther` 시 버퍼 초기화 |
| `FavoriteChannels` | 추가·삭제(토글), 정렬, `nextAfter(current)` |
| `TVChannelController` | 버튼 이벤트 수신 → 위 객체·`ITuner` 조율만 |

### 3.2 O — Open/Closed (개방-폐쇄)

**질문:** 새 버튼 기능 추가 시 기존 코드 수정 없이 가능한가?

| 점수 | **4 / 10** |
|---|---|

#### 현재 구조

- 각 버튼이 **전용 메서드**(`pressNumber`, `pressFavorite`, …)로 고정되어 있다.
- 확장점(Command/Handler/Strategy)이 없다.
- 새 버튼(예: `pressMute`, `pressLastChannel`) 추가 시:
  1. `TVChannelController.h`에 메서드 선언 추가
  2. `TVChannelController.cpp`에 구현·상태 분기 추가
  3. 기존 메서드와 버퍼·즐겨찾기 상태 간 상호작용 검토

```3:16:src/TVChannelController.cpp
void TVChannelController::pressNumber(int digit) { }
void TVChannelController::pressConfirm() { }
void TVChannelController::pressFavorite() { }
void TVChannelController::pressNextFavorite() { }
void TVChannelController::pressOther() { }
```

#### 판정

- **튜너 구현 교체**는 `ITuner` 덕분에 OCP에 유리하다.
- **버튼·입력 정책 확장**은 OCP에 불리하다. “수정 없이 확장”이 아니라 **기존 컨트롤러 수정**이 기본 경로다.

#### 개선 방향

- 버튼 ID → `IChannelCommand` 실행 맵/레지스트리
- 또는 `press(ButtonId id)` + 핸들러 등록으로 **새 클래스 추가**만으로 기능 확장

현재 프로젝트 규모에서는 과한 설계일 수 있으나, README에 버튼 종류가 늘어날수록 OCP 점수는 더 낮아진다.

### 3.3 L — Liskov Substitution (리스코프 치환)

**질문:** `ITuner` 구현체 교체 시 문제없는가?

| 점수 | **7 / 10** |
|---|---|

#### 현재 구조

```4:10:include/ITuner.h
class ITuner {
public:
    virtual ~ITuner() = default;
    virtual std::string seekCH() = 0;
    virtual void setCH(std::string ch) = 0;
    virtual std::string getCurrentCH() = 0;
};
```

```24:24:include/TVChannelController.h
    explicit TVChannelController(ITuner& t) : tuner_(t) {}
```

- `FakeTuner`, `MockTuner` 모두 `ITuner`를 구현하며 테스트에서 주입 가능하다.
- `FakeTuner::setCH`는 `0~99` 범위 밖에서 `std::invalid_argument`를 던진다.

#### 판정

| 항목 | 평가 |
|---|---|
| 구현체 교체 | ✅ 생성자 주입으로 런타임·테스트 시 교체 용이 |
| 계약 일관성 | ⚠️ 채널이 `std::string`이라 `"01"` vs `"1"` 등 포맷 차이 가능 |
| 예외 정책 | ⚠️ 범위 오류를 던지는지 무시하는지 구현체마다 다를 수 있음 |
| `seekCH` 의미 | ⚠️ `FakeTuner`는 `available_` 기준 순환, 실제 튜너는 다른 의미일 수 있음 |

컨트롤러가 `ITuner`에만 의존하므로 **치환 자체는 가능**하나, **강한 계약(타입·불변식)이 없어** LSP 위반 여지가 남는다.

#### 개선 방향

- 채널을 `int` 또는 `Channel` 값 객체로 통일
- 인터페이스 주석 또는 테스트로 “0~99, 잘못된 입력 시 예외” 계약 고정

### 3.4 I — Interface Segregation (인터페이스 분리)

**질문:** 미사용 인터페이스 메서드 의존이 없는가?

| 점수 | **6 / 10** |
|---|---|

#### 현재 구조

`ITuner`는 메서드 3개뿐이라 **과도하게 비대하지는 않다.**

| 컨트롤러 기능 (의도) | 필요한 `ITuner` API |
|---|---|
| 숫자 입력·확정 | `setCH`, (선택) `getCurrentCH` |
| 선호 채널 토글 | `getCurrentCH` |
| 다음 선호 채널 | `getCurrentCH`, `setCH` |
| `pressOther` / 채널 탐색 | `seekCH` |

#### 판정

- **한 인터페이스에 묶임:** `MockTuner`·`FakeTuner`는 사용하지 않는 메서드도 **항상 3개 모두** 구현해야 한다.
- **기능별 최소 의존 아님:** “채널만 설정하는” 클라이언트와 “탐색만 하는” 클라이언트를 나누지 않는다.
- 프로젝트 제약으로 `ITuner.h` 수정이 어렵다면, **현 수준의 ISP는 수용 가능**하나 점수는 중간이다.

#### 개선 방향 (선택)

```cpp
struct IChannelReader {
    virtual int currentChannel() const = 0;
    virtual ~IChannelReader() = default;
};

struct IChannelWriter {
    virtual void setChannel(int channel) = 0;
    virtual ~IChannelWriter() = default;
};

struct IChannelSeeker {
    virtual int seekNextChannel() = 0;
    virtual ~IChannelSeeker() = default;
};
```

실무에서는 `ITuner` 하나로 유지하고, **컨트롤러 내부에서 필요한 메서드만 호출**하는 것으로 타협하는 경우가 많다.

### 3.5 D — Dependency Inversion (의존성 역전)

**질문:** 구체 클래스가 아닌 추상화에 의존하는가?

| 점수 | **8 / 10** |
|---|---|

#### 현재 구조

- `TVChannelController`는 `FakeTuner` / `MockTuner` / 실제 튜너를 **직접 참조하지 않는다.**
- `ITuner& tuner_`만 멤버로 보유하고 생성자에서 주입받는다.
- 테스트는 `FakeTuner`·`MockTuner`를 **바깥에서** 만들어 주입한다.

#### 판정

| 항목 | 평가 |
|---|---|
| 고수준 모듈 → 추상화 | ✅ 컨트롤러 → `ITuner` |
| 저수준 모듈 → 추상화 | ✅ `FakeTuner` / `MockTuner` → `ITuner` 구현 |
| 구체 클래스 직접 의존 | ✅ 컨트롤러 헤더에 없음 |

**SOLID 5원칙 중 가장 잘 지켜진 항목**이다. TDD·테스트 더블 구조와도 일치한다.

#### 감점 요인

- `getFavoriteChannels()`가 `const std::vector<int>&`로 **내부 컨테이너를 그대로 노출** — DIP와는 별개이나 캡슐화·테스트 결합도 이슈
- 구현이 비어 있어 DIP의 이점이 **동작으로 검증되지 않음**

### 4.4 얇은 컨트롤러 (SRP + DIP 유지)

```cpp
// src/TVChannelController.cpp (개선 방향 스케치)
void TVChannelController::pressNumber(int digit) {
    input_.pressDigit(digit);
    if (input_.isTwoDigitComplete()) {
        applyChannel(input_.consume());
    }
}

void TVChannelController::pressConfirm() {
    if (input_.hasPending()) {
        applyChannel(input_.consume());
    }
}

void TVChannelController::pressFavorite() {
    favorites_.toggle(tuner_.currentChannel());
}

void TVChannelController::pressNextFavorite() {
    if (!favorites_.empty()) {
        int next = favorites_.nextAfter(tuner_.currentChannel());
        applyChannel(next);
    }
}

void TVChannelController::pressOther() {
    input_.clear();
}

void TVChannelController::applyChannel(int ch) {
    if (!isValidChannel(ch)) {
        throw std::invalid_argument("channel out of range");
    }
    tuner_.setChannel(ch);
}
```

## 7. 결론

| 관점 | 요약 |
|---|---|
| **강점** | **DIP(8점)** — `ITuner` 추상화와 생성자 주입으로 테스트·교체가 용이하다. |
| **약점** | **OCP(4점), SRP(5점)** — 기능이 채워질수록 `TVChannelController`가 비대해지고, 새 버튼마다 기존 클래스를 수정해야 한다. |
| **보완** | **LSP(7점), ISP(6점)** — 인터페이스 크기는 적당하나, 채널 표현·예외·`seekCH` 의미를 계약으로 명확히 할 여지가 있다. |

**한 줄 요약:** 의존성 방향(DIP)은 TDD에 적합한 좋은 출발점이나, **입력·선호 채널·채널 적용을 한 클래스에 두는 설계는 기능 구현과 함께 SRP·OCP 부담이 커진다.** Green 구현 후 `ChannelInputBuffer`·`FavoriteChannels` 분리와 `applyChannel()` 중심 리팩토링을 권장한다.
